CEO report · project files in Google Drive

One folder per board

You asked whether project files can live in your users' own Drive, with invited people seeing only that board's folder. They can. Google's own API description confirms the narrowest scope does everything the design needs — including the sharing. I had this wrong in the first review, and the correction runs in your favour.

Decision

Build it. The scope carries the safety.

green light

The correction. I told you the collaboration problem was fatal — files landing in one person's Drive, invisible to everyone else. Your constraint is the fix: if Signal Studio shares the board's folder with the board's members, they get access automatically. Request-access becomes the rare fallback you already tolerate, not the default experience.

Why I can now say that with confidence. The open question was whether an app holding only the narrow drive.file scope may manage sharing. Google's machine-readable API description — pulled directly, three days old — lists exactly two scopes for permissions.create: drive and drive.file. The narrow one is sufficient. Create the folder, share it with named people, revoke them later, upload into it: all of it, on the scope that needs no security assessment.

And it buys more than I credited. Drive's documented maximum upload is 5 TB with resumable sessions. Your product's real ceiling today is about 8 MB. This isn't a cost play — it's a capability play, and that's a much better reason to build it.

What this means commercially

drive.file is non-sensitive. No CASA security assessment, no annual audit fee, and the 100-user cap on unverified apps applies to sensitive and restricted scopes — not to this one, once the consent screen is published. Your only obligation is publishing the OAuth consent screen out of Testing.

What the consent screen will say

The drive.file grant reads to the user as roughly “See, edit, create and delete only the specific Google Drive files you use with this app.” For a wedding planner or a venue manager, that is a reassuring sentence. The broad scopes read as “see and manage all your files” — which is the sentence that loses signups.

One real constraint, worth knowing now

Drive permissions inherit downward and inherited permissions cannot be reduced on an individual item. So everything in a board's folder is visible to everyone on that board. That is exactly the model you asked for — but it means there is no such thing as a private file inside a shared board folder. Anything needing tighter control has to stay in Signal Studio's own storage, which is why the fallback path below is not optional.

Your first question, answered

Three walls between an invited guest and the rest of a Drive

You asked that invited users reach only that board's folder — not other folders, and definitely not the whole Drive. Here is how each of those is prevented, and by whom.

Wall 1 · Google, not us

Under drive.file the app can only ever touch what it created. Alice's photos and tax returns are not "files we promise not to look at" — they are files Signal Studio cannot see, list, or name. A bug in our code cannot reach them, because the token does not carry the right. This is the strongest form of the guarantee you asked for.

Wall 2 · never share the parent

The Signal Studio folder exists only to keep the user's Drive tidy. Sharing it would expose every board at once — the single most dangerous mistake available in this design. It must be a hard invariant with a test that fails the build, not a convention.

Wall 3 · this board's people only

Grants are created per board folder, per member, by email, at a role derived from their Signal role — never type: "anyone", never type: "domain". Both of those should be forbidden in code, so no future change can quietly turn a board folder into a public link.

Who does not get access

Share-link guests. Signal Studio's share links are anonymous bearer tokens with no person behind them — there is no Google identity to grant, and inventing one would be a link-shared folder, which is exactly the loosening you ruled out. Guests keep seeing only what Signal renders.

The design

One connection per board, not one per person

The most important design choice, and the one that makes the experience feel like nothing at all for everyone except the person who sets it up.

A board nominates a storage owner — the person who connects their Drive to it, normally the project owner. Every upload to that board, by any member, is written using the storage owner's credential into the storage owner's board folder. The other members never connect anything, never see an OAuth screen, and never think about Google at all. They drag a file onto a task exactly as they do today; it lands in the shared folder; they can open it in Drive because the folder was already shared with them.

The alternative — every member connecting their own Drive — fails on the platform's own rules: a folder created under Alice's grant is not automatically visible under Bob's, so Bob would have to hunt it down through a picker before his first upload. That is a per-member setup tax for no benefit. One connection per board is both simpler and better.

The upload path is the sleeper win

Today every attachment is posted to a Signal server action, which caps the real file size at about 8 MB and buffers the whole file in memory. Uploading browser-to-Drive removes both problems at once: no body limit, no memory pressure, no egress, and a documented ceiling of 5 TB. Signal mints the upload session server-side and hands the browser only that session URL — the access token never leaves our server.

What we store

Three tables, and one of them is the security control

-- 1 ─ the person's Google grant. Per user, never per board.
CREATE TABLE provider_connections (
  id, user_id, provider,
  provider_account_id,      -- Google's `sub`: catches "reconnected a DIFFERENT account"
  refresh_token_cipher,     -- AES-256-GCM. Access tokens are never stored.
  key_version, scopes, status, connected_at, last_used_at
);

-- 2 ─ which Drive backs which board, and where its folder is.
CREATE TABLE workspace_storage (
  workspace_id PRIMARY KEY,
  connection_id,            -- the storage owner's grant
  folder_id,                -- the board's folder. The ONLY place uploads may land.
  folder_web_view_link,
  state                     -- active | needs_reauth | folder_missing | quota_full
);

-- 3 ─ THE SECURITY CONTROL. One row per person we granted, with the
--     Drive permission id we got back. Without this you cannot revoke
--     precisely, and you cannot prove who has access.
CREATE TABLE drive_folder_grants (
  workspace_id, user_id,
  permission_id,            -- returned by permissions.create
  granted_email, role,      -- 'writer' | 'reader'
  granted_at,
  revoke_pending            -- set when a delete failed; the repair pass drains it
);

-- resources gains: storage ('signal'|'drive'), external_id (Drive file id),
-- connection_id, stored_path. attachments is left alone.

drive_folder_grants is the table that makes the safety claim checkable rather than aspirational. Because we keep the permission id we were given, removing someone deletes exactly the grant we created — not a guess, not a scan. And because we know what we granted, we can show an owner a live list of who has access to their board's folder and reconcile it against Drive's own answer.

A screen worth building on day one

In board settings: “Who can open this board's files.” Names, roles, and a live check against Drive. It turns the whole feature from something the customer has to trust into something they can see — and it is the screen you will want the first time someone asks whether an ex-supplier still has the contract.

What to worry about

The risks this model actually introduces

Ranked by what would hurt most. The first one is the only one I would lose sleep over.

highest

A removed member keeps Drive access

Someone leaves the board, the revoke call fails — expired token, network blip, owner disconnected that morning — and they quietly keep the contract forever. Signal's UI says they are gone. Drive says otherwise. This is a security failure that looks like success, and it is the genuine new risk your model creates.

The answer, in three parts: revoke inline on removal; if it fails, record revoke_pending and retry on a schedule; and show the truth on that access screen — read live from Drive, not from our own table. Never let our record of a revocation stand in for the revocation. There is no background worker in the codebase today, so this needs a small scheduled job added deliberately rather than assumed.

high

The board's files live in one person's personal Drive

If the storage owner leaves the company, closes their Google account or simply stops paying for storage, the board's files go with them. This is inherent to the model, not a bug in it — and it is survivable if it is never a surprise.

The answer: say it on the board, permanently — “This board's files are stored in Alice's Google Drive.” Block the storage owner from leaving without handing over. Build the handover flow before launch, not after the first support ticket. And keep Signal's own storage as a live fallback so losing the Drive never stops work.

medium

The email we share to is not their Google account

We hold the address they signed up to Signal with. If that is not a Google account, the share still gets created and they land in request-access — the case you said you are comfortable with, and I agree it is fine. It just should not be silent.

The answer: let people add a Google address to their profile, and show the grant state per member on the access screen so an owner can see who is actually in versus who is pending. Turn an invisible failure into a visible row.

medium

Privacy terms now describe someone else's Drive

Once a supplier's file lands in the owner's personal Drive, the owner holds that data and Signal Studio does not. Under GDPR that is a real change in the story you tell customers, and it affects account deletion: if a member deletes their Signal account, we can remove our rows but we cannot — and must not — delete files that now belong to someone else.

The answer: a paragraph in the privacy policy and a sentence at the point of connection. This is a founder task with a lead time, not an engineering ticket, which is why it is in this report and not the backlog.

manageable

Duplicate files from retried uploads

A retried upload that already succeeded creates a second copy, and Drive is happy to hold ten identical contracts. The answer: stamp each upload with a Signal id in appProperties — a field Google keeps private to our app — and look it up before any retry. One decision, made once, and the entire class disappears.

Economics

The money was never the argument — but it does improve

What leaves Signal Studio

Storage and egress for Drive-backed boards go to roughly zero, because the member's browser talks to Drive directly in both directions — up on upload, down on preview. Not a large number today, but it stops being a number that grows with your customer count. The thumbnail problem disappears too: Drive renders its own previews.

What stays, and what is new

Metadata rows, the OAuth infrastructure, encrypted token storage, the reconcile job, and support. Drive's API is free within 12,000 calls per minute per user, which you will not approach. The honest new cost is support: some questions will now be answered inside Google's UI, where you cannot see what the customer sees.

The real return is not the hosting bill. It is that a venue can attach a 400 MB walkthrough video to a task — something the product cannot do at all today — and that the file lands somewhere the customer already trusts, already backs up, and already knows how to search.

Scope

What to build, and what to leave alone

Version one

  • ✓Connect Drive to a board, as its storage owner. One folder created, shared with every current member.
  • ✓Drag-and-drop upload, browser straight to Drive, resumable, no size ceiling.
  • ✓Attachments render natively; preview embeds Drive's viewer; “Open in Drive” works.
  • ✓Membership sync on invite, removal and role change — with the pending-revoke repair path.
  • ✓“Who can open this board's files”, read live from Drive.
  • ✓Fallback to Signal Studio storage when Drive is absent, full, or disconnected.
  • ✓Storage-owner handover, and a block on them leaving without it.

Deliberately not yet

  • ✕Picking existing Drive files. Genuinely useful, entirely additive, and it needs a second Google component — it should not delay this.
  • ✕Shared Drives. The narrow scope cannot enumerate them and they are a paid Workspace feature your market largely lacks.
  • ✕Two-way sync and change watching. Refresh a file's details when someone opens it; that is enough.
  • ✕A folder per task. One per board is the unit people think in — and the unit you asked for.
  • ✕OneDrive, SharePoint, Dropbox. The shape generalises; adding a second provider now doubles the surface for no learning.
  • ✕AI over documents. It needs the file's contents, which brings the bytes back through our servers — a separate decision with its own privacy story.
