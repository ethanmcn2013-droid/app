Why I cannot do the next four for you

Google deliberately has no programmatic way to create a consent screen or an OAuth client for a web app. There is no command, no key, and nothing I could install would change that — I checked before saying so. These four screens are human-only by design, which is the same design that stops anyone else automating their way into your account.

Separately, and regardless of the above: I do not sign into accounts or handle passwords. That line is worth keeping even when it is inconvenient.

The thing that changes what these screens mean

Your signal-studio project already holds a credential called Clerk production. That is what powers Sign in with Google for every customer you already have, and this project’s consent screen is already serving it.

Nothing below is dangerous, but you are adding to a live setup, not filling in a blank one. One rule covers all four screens: if something is already there, add beside it — never clear it out.

What is left

Four screens, in this order

Each link opens the exact page with your project already selected. The dashed blocks are clicks, the dark blocks are things to copy, the light blocks are what you should see back.

  1. 1

    Branding — read it before you change it

    Open console.cloud.google.com › auth › branding

    This screen is already live — it is what people read when they sign in with Google today. If the app name already says Signal Studio, leave it alone. Fill in only what is empty:

    • App home page: https://signalstudio.ie
    • Privacy policy: https://signalstudio.ie/privacy
    • Terms of service: https://signalstudio.ie/terms
    • Authorised domain: signalstudio.ie
    If it goes wrong

    Do not upload a logo. The slot is there and it looks like it wants filling. It puts the whole app into Google’s brand-review queue for days and buys us nothing we need today.

  2. 2

    Audience — check the status, publish only if it says Testing

    Open console.cloud.google.com › auth › audience

    Look at the publishing status first. If it already reads In production, this screen is done — Clerk’s sign-in will have needed it. Change nothing and move on.

    If it reads Testing, press Publish app and confirm.

    You should see
    Publishing status: In production
    Why this one is worth not skipping

    Left on Testing, Google silently discards every Drive connection after seven days. Customers would connect, it would work all week, and the following Monday it would be broken with nothing in our logs to explain it — indistinguishable from a bug in our own code, a week after we stopped looking for one.

  3. 3

    Data Access — add one permission to the ones already there

    Open console.cloud.google.com › auth › scopes
    Add to this list. Never clear it.

    There will already be entries named something like userinfo.email, userinfo.profile and openid. Those are what Google sign-in uses. Leave every one of them ticked. Removing them breaks sign-in for every customer you have.

    Press Add or remove scopes. Paste this into the filter box, tick the one result it finds, then Update and Save.

    Copy this
    https://www.googleapis.com/auth/drive.file
    You should see
    Your non-sensitive scopes    3 or 4 — the sign-in ones, plus ours

.../auth/userinfo.email      already there, leave it
.../auth/userinfo.profile    already there, leave it
openid                       already there, leave it
.../auth/drive.file          See, edit, create and delete only the specific
                             Google Drive files you use with this app
    If it goes wrong

    If something lands under sensitive or restricted scopes, you ticked the wrong Drive entry — untick that one only. The ones to avoid are drive, drive.readonly and drive.metadata: each reads a customer’s entire Drive, and each triggers an annual third-party security audit we neither want nor need.

  4. 4

    Clients — create a new one, do not touch the old one

    Open console.cloud.google.com › auth › clients › Create client
    The one place a wrong click costs you customers

    Clerk production is in this list. Do not open it, edit it, or delete it — it is what makes Sign in with Google work for everyone who already has an account. Press Create client and make a second, separate one. A project may hold as many as it likes.

    • Application type: Web application
    • Name: Signal Studio Drive

    Under Authorised redirect URIs, press Add URI twice and paste one into each. These are the only two addresses Google will send a person back to — anything else is refused, which is what stops somebody redirecting your customers elsewhere.

    Copy this — first URI
    https://app.signalstudio.ie/api/connections/google/callback
    Copy this — second URI
    http://localhost:3000/api/connections/google/callback

    Press Create.

    Then press Download JSON

    A panel appears holding a client ID and a client secret. The secret is shown once. Press Download JSON — it lands in your Downloads folder. That file is all I need, and it means the secret never goes through our chat.

    If it goes wrong

    If the second address is refused with “Invalid Redirect: must use a secure scheme”, check you typed http and not https on the localhost one. Google allows plain http only for localhost, and it is strict about it.

Then send me one line

I will find the downloaded file myself and put both values into Vercel, so you do not have to open Vercel at all. Just tell me it is there, and give me the second Google account — an email address is not a secret.
