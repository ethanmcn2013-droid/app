No Notes rows, credentials, production configuration or product visibility were accessed or changed. The product brief requires removing the Notes app, archiving its production data, and leaving Chat Saved notes unaffected. This document prepares the concrete scope and recovery evidence for that final decision; it does not grant execution authority.

Important incompatibility: `listArchivedNotes()` in `src/modules/notes/server/actions/notes.ts` currently requires **both** non-null `archivedAt` and non-null `promotedTaskId`. Merely setting `archivedAt` on unpromoted notes would make them disappear from both current lists. A purpose-built authenticated archive reader/export must be implemented and verified before any archival release. It must read the owner's retired notes without requiring task promotion and must never expose raw Notes bodies to Project collaborators.

`archivedAt` already has product meaning: past promotion/archive. Preserve every existing non-null value, including zero; do not globally clear archive fields during rollback. Completed outbox receipts bind approved extraction and task links permanently. Pending outbox records can mean Tasks accepted a request while Notes lacks its response. A pending/unknown/inconsistent outbox blocks retirement. Reconcile the exact existing operation via its established receipt protocol before preparing a fresh snapshot; never retry by creating a new operation or assume a missing response means no Task exists.

## Offline inventory utility

`scripts/notes/retirement-inventory.mjs` accepts a **previously supplied local** JSON download in the existing `/api/account/export` shape (`product`, `clerkId`, `exportedAt`, `notes.available`, `notes.notes`, `notes.noteTaskSendOutbox`). It does not fetch the account export, load environment files, import an application/database client, run SQL, or contact a service. A missing/unavailable Notes module or absent outbox array fails; an empty array is an explicit input observation, not proof that a database was queried completely.

```text
node scripts/notes/retirement-inventory.mjs --input PRIVATE_EXPORT_JSON --owner EXACT_CLERK_ID --out PRIVATE_NEW_MANIFEST_JSON --source-revision EXACT_40_CHARACTER_APP_COMMIT
node --test scripts/notes/retirement-inventory.test.mjs
```

Run only after the coordinator arranges authorized private export custody. No export was obtained for this preparation. The utility validates single-owner rows, duplicate IDs, exact prior archive state, timestamps and completed receipt bindings. Pending, unknown or missing outbox status fails closed. Metadata output allowlists immutable note/owner/receipt/Task/workspace IDs and original dates; it excludes bodies, extracts, pending approved wording, capture addresses, calendar identifiers, credentials, Chat data and all other modules. The output and source export are private files; do not attach them to GitHub, public Pages or routine run logs. Stdout contains only counts and the metadata-manifest hash; errors contain fixed codes.

The output file is create-only, preserving existing files and the input. It carries the input SHA-256, source revision and deterministic manifest SHA-256. It always states `preparationOnly: true`, `eligibleForProductionApply: false`, and `sourceConsistency: unverified-account-export`. An account export uses multiple reads and is not a transactional cutover snapshot. This utility cannot prove database identity, completeness, concurrent-write absence, task-link existence in another database, ciphertext custody or source authenticity. A fresh transaction-backed production inventory and recovery backup remain required later. No synthetic counts in the tests are production counts.

## Reversible cutover proposal, after separate implementation and review

1. **Prepare and rehearse without production writes.** Implement the owner-authenticated read-only Notes archive, old-link compatibility and server mutation gate on isolated fixtures. Test active/unfiled/already-archived/promoted notes, pending outbox refusal, completed receipt binding, cross-owner denial, account export/erasure and unchanged Chat Saved notes. Direct old Notes links should render the archive/read/export explanation after cutover; no silent redirect into Chat and no task promotion to make notes visible. No new note creation should be possible through an old tab or direct server action once the gate is active.
2. **Observe exact targets under coordinator custody.** Obtain current App source/release/flag revision, explicit Notes database identity hash, authorized owner set and complete owner-scoped counts. Inventory every Notes write producer and any external inbound route. Record task source IDs and completed receipt edges against independently authorized Tasks reads; do not repair or remove orphaned references during retirement. Resolve pending/uncertain outbox separately, then restart inventory.
3. **Prepare encrypted recovery custody.** Take a consistent Notes read-transaction backup with full rows, DDL, indexes, triggers, FKs and related tables. Existing `scripts/db/backup.mjs` is a read-only dump primitive; `backup-all.mjs --verify` restores a temporary copy but writes plaintext. Neither is an encrypted production-custody procedure. `production-backup-custody.mjs` is explicitly bound to Tasks' production URL fingerprint; never pass Notes credentials to it or weaken that binding. A separately reviewed Notes-specific ciphertext wrapper/custody receipt is required before applying retirement. Pin the Notes identity independently, checksum-pin the encryption binary, use the approved public recipient, retain decrypting identity separately, and upload only ciphertext plus sanitized receipts. Decrypt/restore into an isolated private target and verify every table hash/DDL, SQLite integrity and FK checks before relying on it. Retain trusted ciphertext/body hashes independently of the downloaded artifact and a durable recovery copy beyond any 90-day Actions retention. Plaintext, OAuth refresh tokens and decrypting identities must remain outside Git/artifact uploads; Windows mode bits alone are not private ACL enforcement.
4. **Present Ethan the exact operation.** Supply owner scope, actual active/already-archived/linked/outbox counts, immutable source/target IDs, reviewed release revision, fresh backup/ciphertext/restore receipts, write-freeze method/window, archive reader proof, exact apply/undo journal schema and retention/custody owner. Ask for explicit production archival confirmation only then. Do not ask him to approve placeholders or interpret this preparation as consent.
5. **Apply only after that confirmation.** Use a reviewed owner-scoped, idempotent transaction under an effective Notes-only write freeze. Capture a fresh quiescent backup and inventory after the freeze (a prior backup can miss newer writes). Establish per-record compare-and-set guards over `id`, `userId`, original `archivedAt` and `updatedAt`, preserving all prior non-null archive values and every other field/link. Record operation ID, note ID, exact before/after archive values and version guards in an immutable private execution journal. Abort the whole owner transaction on any drift, missing note or unresolved outbox. The offline utility here emits no update/undo SQL and cannot perform this step.
6. **Verify before releasing the freeze.** Counts and IDs reconcile exactly; changed active rows have the operation's archive timestamp; prior archives and all content/receipt/task links are unchanged; second execution is a no-op. Verify owner archive read/export, old links, server mutation refusal, privacy lifecycle and unaffected Saved notes/Project conversations/Tasks. Observe the intended deployed alias/revision, not merely a green build. Keep failed/partial receipts and stop dependent release rather than broadening writes to make totals agree.

Cross-store reads/backups are not atomic together. Record each timestamp and target independently; freeze related Notes send activity and verify edges against the receiving Tasks snapshot before any later archive claim. Do not restore a complete Tasks database to undo a Notes retirement.

## Recovery specification

Ordinary rollback uses the exact execution journal: restore `archivedAt` only for IDs changed by that operation, scoped to the original owner, and only if each row still matches the operation's after-value and expected version. Restore the exact old value (including null), not a default. Leave previously archived rows, new rows, later legitimate edits, bodies, extraction bindings and Tasks untouched. Any mismatch requires reviewed conflict resolution; no blanket unarchive. Re-enable a Notes write path only through the reviewed release/flag reversal after archive compatibility and pending-send safety are checked.

Disaster recovery first restores the encrypted full Notes backup into a new isolated target, verifies hashes/DDL/integrity/FKs, then proposes a separately authorized targeted reconciliation. Never overwrite live Notes wholesale because another module failed, and never clone private Notes into Chat as recovery. Retain note IDs, original timestamps, `promotedTaskId`, Tasks `source_note_id`, outbox operation/task identities and spawn ledger links. Account erasure requests remain authoritative and must not be reversed by restoring an older backup; apply the established deletion/tombstone custody rules before any live recovery.

## Prepared backup wrapper and staging procedure

`scripts/db/notes-backup-custody.mjs` is an offline adapter over the shipped backup-bundle/encryption preflight/age engine and the shipped local restore verifier. It has only `prepare` and `recover` commands. It accepts no URL, token, connection, migration or archival argument and reads no credentials. The independently supplied body, manifest, raw manifest hash, Notes identity and source commit must agree. The wrapper also checks an independent canonical manifest hash on recovery, checksum-pins the age executable, refuses a dirty/wrong source checkout, requires new private output directories outside the repository, verifies every restored table hash and DDL plus integrity/FKs, and emits only `backup.age` plus an allowlisted receipt in the ciphertext directory. Its temporary private restoration/bundle directory is checked and removed after successful preparation. On failure it preserves possible private state for controlled recovery; never upload that state.

The supported Notes schema is the five canonical module tables in `drizzle-notes/0000_notes_baseline.sql`. Unknown tables or another module cause refusal before restore. Source search references a historical `notes_fts` table although the tracked baseline does not define it. If a fresh authorized inventory discovers FTS shadow tables, extra migration tables or other schema, stop and add reviewed full preservation/replay support using the observed immutable schema; do not omit the tables, delete/rebuild them in production, or weaken the allowlist to get a green receipt.

The wrapper does not obtain the original read-transaction dump, prove its freshness, upload ciphertext, establish independent escrow or mutate a source database. Its receipt says `sourceConsistency: unverified-supplied-dump`, `artifactUpload: not-performed` and `productionMutation: none`. Tests inject a synthetic age process to verify delegation/binding/custody behavior; that is not evidence of real ciphertext or real key recovery. A real approved age binary and a separately held identity are still required for the authorized rehearsal.

Server-rendered component tests verify old-link selection, escaped private content and no edit controls; browser/layout verification of the disabled-by-default alternate surface remains a receiving gate before activation.
2. Plain `backup.mjs` invocation alone does not assert a transaction-backed cutover snapshot. No source backup was acquired for this work.
3. In the clean reviewed checkout, run `prepare` with explicit local private inputs, trusted independently retained hashes/identity, approved recipient and checksum-pinned age binary. All placeholder paths/hashes below must be real private values; none are filled in by this preparation:

```text

Then the coordinator can present the concrete archive/freeze/release operation for Ethan's required approval. No prepared command changes `NOTES_RETIREMENT_ARCHIVE_ENABLED` or archives a row.
