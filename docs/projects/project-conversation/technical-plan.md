## Recommendation and integration boundary

Build a bounded conversation domain inside the existing Next.js application and Tasks libSQL database. Keep Clerk identity, canonical Project membership, task records and private Notes ownership. Use authenticated, uncached delta retrieval as the first transport experiment; a durable outbox handles directed delivery separately. There is no new identity provider, AI dependency or shared chat database service in the proposed initial slice.

```text
Project / Messages / canonical Task Discussion
        -> Clerk identity + exact resource / audience check
        -> conversation service -> Tasks libSQL transaction
                                -> message + revision + outbox intent
        <- receipt only after commit
Other tab -> authenticated delta/history retrieval -> current authorized content
Source transaction -> canonical in-app attention
Outbox worker -> current recipient policy -> eligible external alert only
Create task -> Tasks service + provenance in same Tasks transaction
Save to my Notes -> durable operation -> idempotent Notes receiver -> recoverable link
```

The existing `ProjectId` is a Tasks `workspaces.id`, not a child of a separate organization workspace. Bind the first conversation to that identity. Do not use Planning Period, tag, Timeline slug, prototype Space or email as its tenant key. The active architecture task explores Spaces and optional tools, but its recommendations are not a committed permission model. An eventual broader workspace may own DMs only after its identity/membership contract exists and a separate migration decision is recorded.

### Representative flows and where reuse stops

1. **Comment:** `ConversationFeed` → `addCommentAction` → task-derived `scopeForTask` → comment INSERT → task touch/activity → seed-handle mentions → notification INSERT → process-local refresh. There is no atomic message+attention commit, durable retry key or edit replay. Preserve the comment identity and replace the mutation contract at its boundary.
2. **Task creation:** explicit `projectId` → `authorizeProjectCandidate` → canonical task insert → activity/sponsored-use side effects → list return. Conversation promotion needs a receipt plus transaction-aware shared task core. A caller-supplied task ID alone does not prove that identical content was previously accepted.
3. **Notes:** `createNote` → Notes `requireUser` → optional Tasks membership check for filing → separate Notes insert. Failed filing can silently become Unfiled today. The new promotion wrapper must disclose the actual result and use a durable cross-store operation; no distributed atomicity is assumed.
4. **Realtime:** task mutation emits in one Node process; `/api/events` subscribes to that process; client refetches. A local demo passing does not prove two Vercel instances synchronize. New polling reads the shared authoritative store and has no process affinity.

## API and transaction contract

Use typed server actions for user mutations and authenticated route handlers for bounded history/sync/search. All accept exact IDs, never ambient-only context. `actor_id` comes from Clerk; workspace is derived from stored resource and checked against any expected route scope. New writes verify Origin/CSRF through existing server-action protection; custom route mutations must implement the same origin/token policy. JSON is strictly allowlisted and size limited.

| Operation | Input → result / behavior |
|---|---|
| `ensureProjectConversation` | `{workspaceId,requestId}` → one canonical conversation; require eligible project member, perform unique insert in transaction. |
| `openDm` | `{workspaceId,peerId,requestId}` → existing/new pair or request-pending; both members eligible, no account discovery outside project, consent/block check. |
| `sendMessage` | `{conversationId,expectedAudienceEpoch,requestId,body,rootId?,mentions[]}` → `{messageId,createSeq,changeSeq,revision,committedAt}` after commit. |
| `getSendReceipt` | same conversation/request key → authorized receipt or `absent`; lack of network response is not absence. |
| `editMessage/deleteMessage` | `{messageId,expectedRevision,expectedAudienceEpoch,requestId,body?}` → new revision/tombstone. Author only for normal edit/delete; reported content removal uses audited operator flow. |
| `listHistory/getThread` | `{conversationId,beforeSeq?,rootId?,limit<=50}` → items, `hasMore`, scoped opaque cursor; hard maximum 100, no offset paging. Unauthorized and missing collapse to `unavailable`. |
| `syncConversation` | `{conversationId,afterChangeSeq,limit<=100}` → current-authorized revisions/tombstones and next cursor from one consistent snapshot. No-store; duplicate/out-of-order deltas safe. Expired cursor returns `resync_required`. |
| `markSeen` | `{scope:{kind:conversation|task,id},observedItems:[sourceId,revision]}` → monotonically set caller's matching attention `seen_at` and merge root/thread coverage; limit 100, validate published identity/current access. Hidden/unloaded messages excluded. |
| `setPreferences/follow` | exact resource, constrained policy fields → persisted settings; no membership writes. |
| `createWork/linkWork` | source ID/revision, destination kind/project, confirmed form, request ID/hash → durable operation + canonical destination receipt. |
| `searchMessages` | `{scope,query,person?,from?,to?,cursor?,limit<=30}` → currently authorized result+snippet; no global counts. |
| `invite/accept/revoke` | scoped guest contracts below; all POST/action, never GET acceptance. |

Common errors: `unauthenticated`, neutral `unavailable`, `read_only`, `audience_changed`, `revision_conflict`, `invalid_input`, `rate_limited(retryAfter)`, `request_conflict`, `temporarily_unavailable`, `resync_required`. Expose archive/epoch detail only after access proof. Unexpected errors return request ID, not SQL or body. Proposed message limit 8,000 characters / 32 KiB UTF-8; normalize line endings before request hash, not user meaning. Mention spans must resolve to active, authorized identity IDs; a mention grants nothing. URLs allow only safe schemes; raw HTML and automatic unfurling excluded.

**Send transaction:** obtain a write transaction, resolve current identity beforehand, prove live membership/consent/block and archive state inside the transaction, compare epoch, check prior request hash, allocate sequence with row increment/RETURNING, insert source and change, materialize eligible in-app attention rows, insert external outbox intent, commit, then acknowledge. A duplicate key with different normalized payload returns `request_conflict`. Recheck authorization before returning a previous receipt; a removed user cannot recover content through idempotency lookup. No Clerk/network/provider calls while a write transaction holds the DB lock.

Writes and access changes must serialize on the primary. Membership INSERT/DELETE/role and workspace archive/delete must increment relevant audience epoch through DB triggers in the same transaction, including raw SQL/erasure paths; triggers also invalidate dependent DM eligibility. New shared participant changes similarly increment their conversation epoch. UI checks are insufficient. Do not hook only `removeMemberAction`: source discovery found other writers. Role-only epoch changes may create extra reviews but cannot silently expand audience. Existing Project revision is not assumed to be an ACL version.

Turso documents write transactions as `BEGIN IMMEDIATE` with primary forwarding and database write serialization; interactive transactions have a five-second timeout. Keep transactions short and verify actual installed driver/primary consistency in EX-01. This is a feasibility dependency, not measured performance. [Turso transaction reference](https://docs.turso.tech/sdk/ts/reference)

### Foundational clarifications from the bounded review

**Epoch topology:** retain one aggregate `audience_epoch` per conversation. Workspace member INSERT/DELETE/role change and workspace archive/restore trigger updates to every conversation whose `workspace_id` matches; Project conversation rows, all Project-scoped DMs and shared rooms linked to that Project are included (over-invalidation is acceptable). Explicit participant acceptance/leave/removal, DM consent/state change, scoped user block/unblock and messaging eligibility change update the affected conversation rows in the same write transaction. For a Project-wide user block/eligibility change, update all conversations in that Project containing the affected user/pair, or conservatively every room there. Account suspension/erasure updates all affected memberships/participants and epochs before acknowledgment. Conversation creation initializes epoch 1 after current-membership proof. No remote Clerk state is assumed to update local rows synchronously: every request checks a valid session and local access; provider revocation/session propagation must be separately tested and disclosed.

The trigger write order is source membership/participant/block change → epoch increment/change-log invalidation → commit. Ordinary membership reacquisition restores inherited Project history under A03, but sets a formerly removed DM participant to `rejoin_pending`; it does not restore DM consent. Restore/archive triggers cannot reset epochs or reactivate participants. Outbox and every receipt/read/mutation reauthorize against this same mapping. PC-01 owns the complete writer inventory and EX-01 tests raw SQL, consent, block, leave, rejoin and archive paths; no undefined “relevant room” predicate may enter implementation.

**DM state machine:** generic pair request `pending` → recipient explicitly accepts → `active`; decline → `declined`; either participant block → pair delivery `blocked`; leave → `left`; lost membership → `membership_lost`. Pending/declined pair has no message-body delivery. Block stops requests/sends/alerts; currently entitled participants can still read already retained history. Leave/removal denies the departing person's history; unaffected participant retains history but cannot send until pair is active. Rejoining membership only creates `rejoin_pending`; both people must confirm reopening the same unique pair, with retained-history disclosure, and any block must first be deliberately lifted by its owner. New messages require both current memberships and active consent. Repeated requests are rate limited and a decline is not automatically retried. These are proposed founder decisions before PC-10.

**Atomic in-app attention:** every source write includes source/change, eligible `conversation_attention` rows and external outbox intent in the same write transaction, for project messages and canonical comments. The worker never owns initial in-app attention creation. A drain outage cannot hide directed activity. Keep the synthetic/pilot audience bounded (proposed max 50 room participants) to test fan-out lock cost; if it fails, revise architecture before raising the cap. Recipient/source checks on reads remove revoked access; edits/deletes adjust attention transactionally. Add a test where source commits and the external drain never runs.

**Canonical Task Discussion API:** `sendTaskComment({taskId,expectedAudienceEpoch,requestId,body,rootCommentId?,mentions})`, `editTaskComment/deleteTaskComment({commentId,expectedRevision,expectedAudienceEpoch,requestId,...})`, `getTaskCommentReceipt({taskId,requestId})`, and `syncTaskDiscussion({taskId,afterChangeSeq,limit})` use the same validated receipt/error contract. Task-derived Project scope, strict archive proof, epoch check, request hash, per-task sequence, canonical comment mutation, activity, change log, attention and outbox commit together in the Tasks write transaction. Reply root must belong to the same task and be top-level. Reads combine activities and comments without mirroring either. Legacy null-tenant rows only backfill if parent task and author context can be validated; otherwise quarantine from new writable adapter and report, never invent tenant. Existing IDs/permalinks remain. PC-10 must test response loss, changed-payload conflict, foreign root, archive/revoke races and legacy rows.

**Private seen state:** these records are reader-private attention state, never sender-visible read receipts or presence. Only the current reader may query/update their event state. Authors, Project owners, other participants and analytics get no per-person read history, timestamp or derived engagement report. Operational access/export follows D-PC10 and may not silently expose it; retention includes coverage/seen rows. Add explicit negative APIs/export/analytics tests. Existing phrase “read receipts” elsewhere means internal bookkeeping only; public read receipts remain excluded.

| Removed/suspended/anonymous/public Timeline viewer | None; neutral unavailable and no informative counts | None | None from conversation; public artifact grants no chat authority | None |

Authorize at the actual query/mutation boundary, including snippets, unread counts, source previews, downloaded objects and async work. This applies the deny-by-default and per-request approach in [OWASP authorization guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html). Database credentials remain privileged because there is no RLS: server module boundaries, tests and a small repository API are essential controls.

**Revocation guarantee:** requests whose authorization snapshot begins after the revocation commit must deny; no content committed after that revocation can reach the removed principal. A response authorized before revocation may already be in flight. Screenshots, delivered email and prior downloaded data cannot be recalled. Reads must use primary/fresh consistency and a single authorization+content snapshot; a stale replica or authorize-then-newer-unscoped-query violates this guarantee. On access loss the client aborts fetches, clears rendered history/query state and removes composer, with a safe return link. Server enforcement does not depend on the client cooperating.

Queued notification jobs always reauthorize and reread the latest source, drop deleted/revoked work, and never carry a stored body snapshot. External pilot alerts use generic wording and an opaque authenticated deep link, without project title, message body, sender name or attachment URL. If revocation races a provider request, this limits content exposure but an already-submitted generic alert may still arrive; disclose that boundary. No provider receipt means no delivered claim.

## Consistency, transport and failure recovery

Client states: **draft** (editable) → **pending** (one immutable submitted request) → **accepted** (committed receipt). Timeout after submission → **uncertain**, not failed. Reconcile original request ID before Retry. Validation/permission rejection → **failed** with recoverable editable text; changing payload creates a new request after the old attempt is resolved or explicitly discarded. Never auto-send after account/project/epoch change. Offline mode is a recoverable draft, not an offline-first delivery promise.

Merge by canonical message ID and revision, replace temporary row by request ID, deduplicate event IDs. Creation sequence orders committed messages; separate change sequence carries edits to old messages. Tombstones remove live bodies/previews/mention attention and preserve thread position. Stale edits yield a version conflict and a copy-preserving compare action; they do not overwrite new text. An edit only creates newly warranted directed reasons and does not repeatedly alert old mentions. Reactions are unique `(message,user,emoji)` acknowledgements with no notification; removing source removes reactions.

Initial **polling experiment**: one active visible conversation request per second with jitter, immediate reconciliation on focus/reconnect, one request in flight per view, exponential backoff to 30 seconds on failure. Hidden tabs pause conversation polling; a visible Messages list uses a coalesced 15-second attention refresh. These are hypotheses. Tab coordination elects a poll leader where supported; failure falls back safely to extra authorized reads. Each request checks authorization even when the cursor is unchanged; do not return a cached 304 across principals. No-store responses and no service-worker history cache.

Do not promise the 1.5-second remote target until EX-02 passes across two application instances. If polling misses the latency/cost ceiling, the named fallback experiment is an opaque user-scoped broker signal followed by the same authorized retrieval. Existing SSE is not the fallback. Supabase's cached channel policies remain a real concern if selected later, but adopting Supabase now adds another backend. Its docs explicitly say policy cache persists for the connection and refreshes on subscribe/new JWT. [Supabase Realtime Authorization](https://supabase.com/docs/guides/realtime/authorization)

A managed chat service such as Stream is a credible later comparison because it supplies channel membership APIs; that is not evidence it matches Signal authorization/revocation. Compare the same EX-01/02 slice plus export/delete, region, support cost and guest policy; do not build two full products. Reject immediate adoption because identity/membership synchronization adds a new authority and unpriced dependency before demonstrating the existing-store limit. Revisit if durable sync cost/latency fails or founder operating burden exceeds budget. [Stream channel membership](https://getstream.io/chat/docs/node/channel-members/)

## Attention contract

Ordinary root messages create a quiet unread marker. DMs, explicit mentions and followed replies create directed events; badge counts **distinct conversations** with unseen qualifying events, not messages or tasks owed. One event with multiple reasons merges reasons, never duplicate alerts. Auto-follow roots you create/reply to/are mentioned in; explicit Unfollow wins until a subsequent explicit mention. Self-actions and reactions do not alert.

Rendered visible ranges produce read receipts; opening a room does not clear hidden replies, paginated-out roots or historic edits never shown. Messages and Inbox use the same event ID/seen operation; opening task reminders does not complete tasks. Explicit Mark all read uses a captured boundary so a concurrent new message remains unread. Multi-device updates merge monotonically; network responses from a previous account are discarded using a session generation key.

Mute suppresses directed badge/interruptions for the conversation while its quiet unread history remains. Quiet hours suppress external delivery only. Recipient time zone is explicit IANA zone, with DST-safe local interval computation. A visible destination lease (proposed 45-second expiry, refreshed while visible) suppresses external alerts; it is not published presence or a read receipt. Coalesce 90 seconds, optional email after 30 minutes still-unread, max one digest per project per hour, all provisional values from the report. Select one opted-in primary device, then configured fallback, never every device. In-app remains usable if push denied; notification permission is requested only after a relevant user action.

## Conversation to work

Task promotion requires source read permission, source revision, explicit destination Project, editable neutral title, confirmed owner and exact date. Server checks assignees against destination members and date semantics with Tasks validation. Same-store transaction creates task, provenance, activity/outbox and operation receipt. Response loss returns the same task; reject request ID reuse with a changed form. Do not automatically copy a private DM excerpt into a broader task: opt-in reviewed excerpt only, audience preview first. Source-link previews require source access even when the destination task is readable.

Use Tasks Schedule/Calendar for ordinary deadlines. Existing milestone curation feeds the primary Timeline; do not silently mark every created task a milestone or publish it. Timeline source/sync tests must remain green. This is a correction to the reports' blanket date expectation, requiring D-PC03 acceptance.

Save-to-note label is **Save to my Notes**. Author writes the outcome; Project filing remains private. For separate Notes DB delivery, first persist a Tasks operation with deterministic destination ID, immutable text digest and actor/source permission version. Notes receiver creates once under authenticated user/service assertion, validates hash, and returns the same receipt; operation recovery later attaches the source link. A retry may leave `destination-created/link-pending`, which is honest and repairable, not a second note. Recheck source permission before content handoff; notes already authored before revocation remain governed by Notes policy. If filing is no longer allowed, offer explicit Unfiled recovery; never report a shared/project-filed success incorrectly. Cross-store creation is not atomic; EX-03 must prove crash points. Team-shared Notes is a separate product project, not an implicit prerequisite.

### Notes operation recovery limit

The Tasks operation retains IDs/hash/status, **not a durable copy of the privately reviewed note body**. An initial call passes the reviewed text from the authenticated in-memory draft to the idempotent Notes receiver, with an assertion bound to actor, operation ID, source revision, destination ID and body hash. On restart or unknown response, first query the owner-authorized Notes receipt by deterministic ID. If present, recover the same note and repair only the authorized link. If absent and the exact reviewed draft is unavailable, enter `needs_review`; do not reconstruct text from the current source or claim unconditional automatic completion. If the source changed/deleted or access was revoked before copying, use `source_changed`/`unavailable`, requiring new review rather than stale copy. A user may resubmit the exact original hash only with current source permission; a changed reviewed form needs a new operation after confirming the prior receiver did not commit. Existing author-owned note remains accessible under Notes policy even if source preview is now unavailable. Search that note only through the owner's Notes domain.

EX-03/PC-12 must inject source edit/delete/revocation at every crash point and assert one note or an honest `needs_review` state, never reconstructed content or duplicate work. This trades unattended recovery before destination creation for avoiding retained private text in the shared Tasks operation store; user review is the explicit recovery path, not a passed automatic-delivery claim.

## Guest contract (separate gate)

Fresh shared conversation for each new external audience. All actual participants can see all retained messages in that room; guest invitations do not grant Project membership. Adding another external recipient to a used shared room instead creates a new room plus a reviewed starting summary. Epoch check at composition/send makes changes explicit. Pending welcome text stays a draft until acceptance and reauthorization, then posts once with stable request ID.

Reuse Clerk sign-in and email UI conventions, not `acceptInviteAction` wholesale: `src/server/actions/settings.ts:701` creates workspace membership, reads primary email but the inspected code does not explicitly inspect verification status, and writes acceptance separately. Those are unacceptable assumptions for the new guest contract, regardless of existing comments claiming verification. New acceptance checks the authoritative email object's verified status and matches the normalized intended address; no provider-specific dot/plus normalization. Verify against installed Clerk types and test verified/unverified/changed-primary cases in EX-04.

Token GET renders generic inviter information only, no confidential room title or message preview; GET/HEAD never consumes token. Require signed-in verified intended account plus explicit POST acceptance; forwarded link alone fails. Seven-day expiry and resend rotation are proposals. Acceptance in a write transaction checks token digest, unexpired/unrevoked state, inviter current management rights, destination lifecycle/epoch, intended history, block policy and capacity; activate participant and consume once. Repeat acceptance by the same authorized actor returns same result; others get neutral refusal. Wrong-account switching retains destination without exposing its content. Email links are authentication, not conversation authorization. [Clerk email-link flow](https://clerk.com/docs/guides/development/custom-flows/authentication/email-links)

Proposed abuse ceilings for pilot configuration: 20 sends/minute/user with burst 5, 10 invitations/day/inviter, 50/day/project, one resend/hour/address. Store counters across instances; return retry time, no dropped accepted posts. Block stops new DM/invite/alert routes, does not pretend another member's Project message vanished. Report is explicit with minimal evidence and an operator response owner. Guests cannot discover public accounts, browse workspace directories, invite others or upgrade themselves. Commercial allowances, retention and support response policy must be approved before real guest data.

## Search, files and lifecycle

Use same-store FTS5 if verified on the target, or bounded parameterized LIKE for the small pilot corpus only if EX-05 meets the search target. Index body tokens without an external search service. Every query joins canonical currently readable resources and nondeleted source rows before ranking, snippets, counts and pagination; guest query is pinned to their one room. Search cannot grant history. Revalidate on open; clear in-memory caches on epoch/account change. No cross-user server cache, title-bearing telemetry or autocomplete of inaccessible people.

Initial pilot is text, safe links and authorized work cards. Reuse upload validation/storage only after conversation association, quarantine/scanning and download authorization pass PC-17. Existing private task attachment access must not be broadened by a chat link. If files become necessary for a guest use case, that use case waits for PC-17. Active HTML/SVG rendering in trusted origin and automatic URL preview fetches remain excluded. [OWASP upload guidance](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)

Drafts live in memory keyed `(user,project,conversation,root)` for navigation continuity; browser-restart persistence is deferred. Retain failed-send text within the same authenticated session; clear message caches, draft text, queued sends and search on sign-out/account change. On revocation remove source history; do not auto-recover/send old drafts. Show recovery copy before a deliberate destructive navigation where applicable. Cap in-memory histories by window (proposed 200 messages) and drafts (20 x 8,000 chars); reaching cap requires explicit save/copy/discard, never silent loss.

Archive freezes new messages/reactions/work association but retains permission-aware history/search and revocation controls. Restore reopens only for currently authorized members. Project duplication copies no conversation, private DM, guest participant or invitation. Account export must filter all sources per subject and disclosed operator policy; erasure must cover sources, index rows, attention, queued deliveries, derivatives and file references with retry custody. Retention duration, backup expiry, legal holds and author pseudonymization remain decisions before real-data pilots. Deleting a source removes live preview; independently authored Tasks/Notes are separate records and must be accounted for, not silently rewritten.

## Operations and later AI

Independent server flags: `CONVERSATIONS_INTERNAL_ENABLED`, `CONVERSATIONS_SEND_ENABLED`, `CONVERSATIONS_GUESTS_ENABLED`, `CONVERSATIONS_ATTACHMENTS_ENABLED`, `CONVERSATIONS_AI_ENABLED`, all default false in every non-fixture environment. Scoped allowlist is server-side. Preserve authenticated history in read-only mode when sends disabled. Schema capability check fails closed, not fallback to fabricated chat.

Conversation outbox drain claims a bounded batch with conditional lease token, releases DB transaction before network, rechecks recipient/source, retries with backoff/jitter, dead-letters after configured attempts (proposed 8), and supports manual replay retaining IDs. Old worker cannot acknowledge a new lease. Provider idempotency and local delivery key handle timeout retries; where provider outcome remains unknown, record unknown and reconcile rather than promise exactly-once email. Separate messaging queue from suite-wide webhook consumers to avoid leaking bodies or disturbing unrelated work. No broad refactor of suite outbox is required.

Log request/event IDs, status/error class, latency, queue age, permission failures, bytes and aggregate cost; exclude bodies, drafts, addresses, tokens, snippets, private titles and secret URLs. Avoid raw exception logging. Alert on stuck leases, oldest pending age, repeated unavailable provider, abnormal denial volume and acknowledged-write discrepancy. Founder owns incident triage and explicit pilot contact path; support can diagnose with IDs. Configuration presence and provider receipts, not a 200 response from a cron, prove delivery.

Migration is additive and ledger/receipt backed; fresh isolated DB starts at supported baseline then forward chain, never historical 0000–0013 replay. No backfill copies comments to new message tables. Validate null-tenant legacy comments before extension; quarantine/report ambiguous rows rather than invent ownership. Roll back application/flags while retaining tables/receipts/history; destructive down migration is a separate data operation. Full operations, cost scenarios and rollback rehearsal are in verification-release.

AI future boundary is a viewer-scoped retrieval service over canonical source IDs+versions; exclude DMs by default. Generation has no write/invite/network-fetch tool authority. Treat source instructions as data, validate access again before display/share, invalidate summaries on edits/deletion/epoch change. Task suggestions require confirmed owner/date/destination. Capture model/configuration/token usage when exposed and separate AI allowance from basic messaging and development-agent allowance. Ordinary history/search remain available without AI. PC-18 requires explicit expansion approval.
