## Immutable operation and receiver contract

Tasks operation unique key: `(actor_id, client_request_id, operation_kind)`. Persist operation ID, authenticated Clerk subject, internal actor ID, source kind/Project/conversation/message-or-comment ID, source revision and reviewed audience epoch, destination kind `private_note`, deterministic note ID, requested filing Project or NULL, exact authored-body SHA-256, canonical full-request hash, state, timestamps and receipt metadata. **No note body, source excerpt, title, draft or snippet** in Tasks operation/link/outbox/logs. The full hash binds filing, actor, source, destination and body digest; changing any reviewed field is a conflict, not an automatic retry.

Receiver creates the note and its immutable operation receipt in one Notes transaction. Unique owner/operation and destination constraints serialize duplicates. The receipt binds operation, owner subject, destination note ID, full-request hash, original body digest, actual filing and commit time. A matching replay returns the original receipt after current owner authorization even if the note has since been edited, archived or deleted. Report `noteAvailable:false` for deletion; never recreate it. A changed payload, forged owner or reused foreign destination is refused without exposing another note.

Use a receipt-only lookup while sends are disabled. A failed lookup means unknown outcome, never absent. Notes owner receipt recovery must not depend on continued source membership: an already authored private note survives source revocation. Tasks provenance lookup/finalization remains separately source-authorized and body-free. A destination-only owner must not recover private source metadata from an opaque link.

For a remote adapter, assertions must be versioned, short-lived, purpose-bound and verified, binding the authenticated subject, internal actor, operation ID, source identity/revision/epoch, destination ID, requested filing and both hashes. Local tests use explicit injected identities and transports; no ambient credentials. Do not pass caller-supplied actor fields through object spreads after canonical identity.

## Crash boundaries and draft custody

1. **Before reservation:** in one Tasks transaction prove a live session-mapped actor, canonical source scope, current membership, exact DM pair/retained-history entitlement where applicable, source revision/tombstone, archive and reviewed epoch. Validate requested filing independently. Reserve IDs/hash/state, commit; make no network call while holding that transaction.
2. **Before content handoff:** resolve the original Notes receipt first. If absent, require the exact in-memory authored draft and revalidate its digest plus fresh source/filing permission. Missing draft → `needs_review`; changed/deleted source → `source_changed`; revoked source → `unavailable`. Never reread current source text to reconstruct a draft.
3. **Notes commit/ack loss:** owner receipt lookup reconciles one note even after process restart. A subsequent owner edit must not change the operation result. Unknown lookup preserves the exact request/key and disables automatic resubmission under another ID.
4. **Before link finalize:** fresh Tasks source proof controls provenance. If source access changed, keep the authored note and expose honest `destination_created/link_pending` or source-unavailable state. Do not destructively compensate by deleting the note. Repair an authorized link once; never send text again solely because the link is missing.
5. **Unfiled recovery:** an explicit choice is required when requested filing can no longer be confirmed. Resolve any existing destination receipt before changing the request; if already committed, report the actual filing. If absent, record a reviewed replacement/cancellation transition with an auditable hash relationship, rather than mutating an unresolved original operation silently.

The UI retains exact authored text, mentions of source context if any, request key and chosen filing in memory while unresolved. Navigation/account changes need scoped custody and stale-generation rejection; never restore another account's draft. If memory is gone, the durable operation can honestly require review without storing private text in Tasks.

**Cross-store ordering limit to settle before implementation:** a signed assertion issued earlier is not fresh source authorization. Name the authorization/content-handoff linearization point and inject revocation immediately around it. A revoke committed before that point must prevent handoff. Separate stores cannot promise that no previously authorized in-flight handoff commits later merely by using a short TTL. Document this limit; if acceptance requires stronger ordering, bring the concrete protocol decision back to the coordinator instead of claiming a two-store transaction.

## Coordinator decision proposal — local handoff ordering

Proposed delegated decision, pending coordinator adoption: a fresh Tasks transaction proves the live canonical actor, exact source entitlement/revision/audience epoch, archive state and reviewed destination, then commits a **body-free handoff authorization generation**. This commit is the authorization linearization point. Revocation committed before it prevents handoff. Revocation afterward prevents new authorization generations, coordinator retry handoffs and source preview; an already authorized in-flight transfer may finish one owner-only private note. Receipt-first recovery reads the original owner receipt and never reconstructs source text. This is an ordered authorization contract, not an atomic transaction spanning Tasks and Notes.

Minimum protocol:

- Bind each authorization to immutable operation/owner/source/destination/hash fields, a monotonic generation, a unique attempt nonce and bounded validity. Record the attempt before dispatch. After uncertainty, query the receiver first; do not resend a body merely because acknowledgment is missing. A confirmed absent attempt requires fresh Tasks proof before authorizing a retry. A cancellation or source-epoch change prevents issuing/reusing a generation for a new coordinator handoff.
- Notes must durably record consumption/cancellation of an attempt and atomically check the expected operation generation while inserting the note plus receipt. Duplicate accepted attempts return the original receipt, including honest note-unavailable state after deletion. Once an absent attempt is cancelled, a delayed request for it must be rejected; only a newly authorized generation can create. Cancellation acknowledgment must mean that this fence committed in Notes, not just in Tasks memory.
- Use a separate **account receiver generation**. Every receive asserts it, and Notes compares it with a durable live account-generation record inside the same Notes write transaction as creation. Unknown, closed or mismatched generations fail closed; do not provision a missing generation from an old assertion. Erasure first closes/advances this receiver generation, serializing against note creation, then removes notes/index/receipts and completes coordinated Tasks cleanup. A receive serialized before the erasure fence is included in deletion; one after it is refused.
- Retain the minimum non-content cancellation/generation fence necessary to reject stale deliveries after erasure. Its representation and retention must be explicit in the lifecycle inventory; deleting every fence and treating missing state as a fresh account would recreate the vulnerability. Tasks cleanup failure must leave retry custody intact, and a Notes fence failure must not be reported as completed erasure or discard the sole recovery record. Account re-enrollment, if ever supported, requires a new explicit generation and current identity proof; it must not revive old operations.

Guarantee: source revocation before authorization prevents copying; source revocation after authorization prevents newly authorized/retried copying; Notes-side erasure fencing prevents late accepted envelopes from recreating the erased account. Each operation yields at most one destination, and lost acknowledgments preserve receipt recovery.

Limit: a previously authorized transfer can finish after source revocation. A delayed first delivery and a replay of an undelivered signed envelope cannot be distinguished by timestamps alone; the receiver's durable consumed/cancelled-attempt state is essential. When cancellation is still unacknowledged, keep the outcome unknown and permit only receipt/cancellation reconciliation, not a changed operation that may duplicate the original. There is no instantaneous cross-store revocation guarantee and no remote transport acceptance in this local contract.

Receiving tests must place barriers immediately before/after Tasks authorization, first Notes acceptance, receiver cancellation, note/receipt commit and account-generation closure. Assert note counts and fencing after process restart with delayed old envelopes, including erasure succeeding in Notes while Tasks cleanup fails.
