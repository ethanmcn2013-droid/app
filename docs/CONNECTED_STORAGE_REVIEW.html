Architecture & product review · connected storage

Reference, not substrate

Google Drive should be somewhere Signal Studio can point, never where Signal Studio keeps a project's files. The proposal's cheap half is the good half — and about seventy per cent of it is already in the schema.

Repo ethanmcn2013-droid/app Read Next 16.2.4 · React 19.2.4 · Clerk · libSQL/Turso ×5 Date 2026-08-27 Code changed none
Panel verdict Recommend with architectural changes invert the premise

The premise contains two features wearing one name. Uploading project files into a user's Drive collides head-on with the tenancy model this codebase is built around, and should not be built. Attaching files that already live in a user's Drive is cheaper, safer, needs no folder tree, no upload pipeline and no quota transfer — and the resources table already has the columns for it.

Storage Drive holds the bytes → Signal holds the bytes; Drive holds what Drive already held
Drive's job substrate → a source you can attach from
Scope drive + folders + sync → drive.file + Picker, nothing else
New tables six entities → one, plus four columns on resources

Already built — reuse it

resources is a provider-aware reference model with provider, externalId and a four-state accessState lifecycle. The paste-a-link path already detects drive.google.com and docs.google.com and renders a Drive chip. The drag-and-drop affordance, the toast rollback, the optimistic row and the removal confirm all exist.

Already designed — the precedent

calendar_connections in the Notes module is a per-user Google OAuth connection table with a provider column “so Microsoft can land later”, a stored refresh token, and a comment choosing polling over push. It is wired into GDPR erasure. No OAuth flow implements it anywhere in the repo — it is a designed stub. Copy its shape; do not copy its plaintext token.

Three defects found on the way through

Blocker · uploads may not work in production at all

chooseBackend() returns vercel-no-token when VERCEL=1 and BLOB_READ_WRITE_TOKEN is unset, and putBytes then throws. DEPLOY.md lists that token under “Optional, provision deliberately”, and src/env.ts does not check it at boot. Confirm the token is provisioned before anything is built on top of this path. Building a Drive integration over an upload path that throws is building the extension before the house.

Contradiction · the real file cap is 8 MB, not 50 MB

Every upload goes through a Server Action, and next.config.ts sets experimental.serverActions.bodySizeLimit: "8mb". But SERVER_UPLOAD_LIMIT_BYTES is 50 MB and the client toast says “is over 50 MB”. A 12 MB PDF fails with a framework error rather than the product's sentence. Fix the numbers or lift the limit — this is true whatever is decided about Drive.

Cost defect · every thumbnail streams the full original

resources-section.tsx renders image thumbnails as backgroundImage: url(/api/attachments/<id>) — a full-resolution file pulled through a Node serverless function to paint a 36-pixel square. The thumbnail column exists in resources and is never written by any code path. This, not the choice of storage vendor, is the dominant egress cost in the current design.

Phase 2 · challenge the idea

Why Drive cannot be the substrate

Three findings decide this, and the first one is fatal on its own.

Finding 1 — the ownership collision

Signal Studio's unit of work is a Project with members. Files belong to the Project: any member can read any Project attachment through an authenticated route, the quota is Project-scoped, and the settings panel is titled “Project storage”.

Google Drive's unit of ownership is one person's My Drive. A file created under drive.file is owned by that person, counts against their 15 GB, and is invisible to everyone else. Signal Studio cannot see it on a second member's behalf either — their OAuth grant is a different grant to a different Drive.

So in the proposed design:

  • →Alice attaches the venue contract. It lands in Alice's Drive.
  • →Bob opens the same task. Signal has the name and size but cannot render the bytes; clicking through gives him Google's “Request access”.
  • →Alice leaves the Project, or revokes the connection — every file she attached goes dark for everyone.
  • →Alice's personal Drive fills up with her own photos, and the product stops accepting attachments.

The escape hatches all fail on this product's actual users. Auto-sharing each file with every member needs each member's Google identity, re-syncs permissions on every membership change, leaks the member list to Google, fires “Alice shared a file with you” emails per attachment, and simply does not work for members who have no Google account — which describes a large share of the wedding suppliers, venue staff and guests this product is built for. Shared Drives fix ownership properly but are a paid Google Workspace feature, which the consumer wedge does not have.

This is not an engineering gap. It is a category error: the proposal silently converts a shared Project resource into a personal one.

Finding 2 — drive.file makes the cheap half the good half

drive.file is classified non-sensitive: no CASA security assessment, and verification is not mandatory for apps using only non-sensitive scopes. drive.readonly and drive are restricted — CASA Tier 2/3, annually, at real cost. That difference alone should pin the scope choice permanently.

But note what drive.file actually grants: files the app created, and files the user hands it through the Google Picker. To let someone attach a file they already have, you need the Picker — and once you have the Picker, you do not need to upload anything at all. Item 8 of the brief, the one listed last as a “should ideally”, turns out to be the whole feature: no folder tree, no resumable uploads, no quota transfer, no reconciliation sweep, no ownership problem that a pasted link does not already have.

Finding 3 — the economics do not carry the argument

At this product's real scale, storage is not a meaningful line item. A thousand paying workspaces averaging even 2 GB is roughly 2 TB; against Vercel Blob's published rates that is tens of dollars a month. That does not justify an OAuth integration, a token-encryption story, a consent screen, a reconciliation worker and a permanent support surface inside a UI the operator cannot see.

Moving bytes to Drive does not remove Signal's costs — it swaps them for token rotation, per-user rate-limit handling, stale-metadata repair, and “why can't my planner open the contract?” tickets. The one economic argument that does survive is the reference model's: a reference has no marginal cost at all. No bytes, no egress, no quota. If a meaningful share of attachments become references, storage growth flattens with none of the machinery.

The recommendation

E, layered on A, with D read as “consolidate onto resources”. Explicitly not B and not C. Drive becomes the first entry in a provider list the schema already has a column for.

What to call it

Not “Google Drive integration” — it names one vendor in a schema built for several. Not “Signal Files” — it promises a storage product that will not exist. Not “Connected Storage” — that is an architecture term, and this repo runs pnpm first-contact:language as a gate precisely to keep phrases like it off the surface. Use what the product already calls it: the section stays Resources, the settings row is Connect Google Drive, and the two intake verbs are Upload from computer and Add from Drive. “Connected storage” is an internal name for an internal seam.

Phase 3 · recommended architecture

One row per attachment, two ways for the bytes to exist

The fork is a column, not a subsystem. Everything above it is unchanged; everything below it already exists on the left branch.

Why the fork is a column

A StorageProvider transport interface would be an abstraction over one implementation, shaped by that implementation. The real variation is not “how do bytes move” — it is “does Signal hold bytes at all”. That is one boolean-ish column, and every downstream rule (quota, delete, download, reconcile) reads cleanly off it.

Why the connection is per user

A Drive grant is a personal credential. Scoping it to a workspace would imply the workspace owns it — the exact confusion this whole review is trying to avoid. Alice's token fetches files for Alice's requests only; using it to serve Bob is a confused-deputy bug, and it is the easy mistake to make here.

Phase 3 · data model

One new table, four new columns

The brief offers six candidate entities. The system needs one of them. attachments is not touched — the union read already handles it, and retiring it is a separate change that must not be coupled to this one.

drizzle/0028_connected_storage.sqlproposed
-- 1 ─ widen `resources` into the canonical file entity.
--     Every column here is additive; no rewrite of the hot table.

ALTER TABLE resources ADD COLUMN storage      text NOT NULL DEFAULT 'signal';  -- 'signal' | 'reference'
ALTER TABLE resources ADD COLUMN stored_path  text;                          -- blob URL or disk path; null for references
ALTER TABLE resources ADD COLUMN connection_id text;                         -- which grant produced this reference

-- task_id becomes nullable so a resource can hang off a Project.
-- SQLite cannot drop NOT NULL in place: 12-step table rebuild, or defer
-- this one column to a later migration. Project-level libraries need it;
-- the MVP does not. RECOMMENDED: defer.

-- Idempotency key for "attach the same Drive file twice".
-- Partial index because SQLite treats NULLs in a UNIQUE index as distinct.
CREATE UNIQUE INDEX idx_resources_provider_identity
  ON resources (workspace_id, task_id, provider, external_id)
  WHERE external_id IS NOT NULL;

-- 2 ─ the one genuinely new entity.

CREATE TABLE provider_connections (
  id                      text PRIMARY KEY NOT NULL,
  user_id                 text NOT NULL,        -- Clerk id. NOT workspace-scoped.
  provider                text NOT NULL,        -- 'google_drive' today
  provider_account_id     text NOT NULL,        -- Google `sub` — detects "reconnected a DIFFERENT account"
  provider_account_email  text,                    -- display only, never a join key
  refresh_token_cipher    text NOT NULL,        -- AES-256-GCM. Access tokens are NEVER stored.
  key_version             integer NOT NULL DEFAULT 1,
  scopes                  text NOT NULL,        -- literal granted scope list, for drift detection
  status                  text NOT NULL DEFAULT 'active',  -- active | needs_reauth | revoked
  connected_at            integer NOT NULL,
  last_used_at            integer,
  last_error_at           integer,
  CHECK(status IN ('active','needs_reauth','revoked'))
);

CREATE UNIQUE INDEX idx_provider_connections_user_provider
  ON provider_connections (user_id, provider);

Identity rules

  • ·Canonical identity is resources.id, always. A Drive file id must never be a primary key: it can attach to two Signal objects, and it is a Google-shaped fact in a Signal-shaped table.
  • ·Provider identity is (provider, external_id). That pair is the deduplication key and the idempotency key, and it generalises to OneDrive unchanged.
  • ·The relationship is the row. One Drive file linked to three tasks is three rows. Removing one must never touch the file.

What is deliberately not stored

  • ·Access tokens. Minted per request, held in memory, discarded. This is already the stated convention in calendar_connections.
  • ·File bytes, for references. Not even a cached preview in v1 — a cached preview is a copy with none of a copy's guarantees.
  • ·Drive folder structure. No folder tree, no project↔folder map. Nothing in the recommended MVP creates a file in Drive, so nothing needs a folder.
  • ·Version history. refreshedAt plus a modifiedTime comparison is enough to say “this changed”; storing versions is a product, not a column.
Latent trap this fixes

removeResourceAction finds an upload's backing row by stripping res- from the resource id. That only works for rows the 0017 backfill created (res-att-…). A freshly minted id is res-<12 hex>, which strips to an attachment id that does not exist. Nothing writes upload-kind resources rows today, so it is dormant — but the first feature that does will trip it. Adding stored_path to resources removes the shadow row and the hack together.

Phase 6 · experience

The connection must never be a prerequisite

The north star puts Experience first and Utility third-but-absolute: someone who has never used a project-management tool must manage unaided. That settles the biggest UX question in the brief.

When nothing is connected

Nothing changes. Drop a file, it uploads to Signal, exactly as today. No banner, no empty-state advertisement, no half-disabled menu item. A storage connection is an optimisation for people who already live in Drive, not a step in attaching a file.

Where the offer is earned

One contextual moment: when a user pastes a drive.google.com link — which the product already detects and already labels “Drive”. That is the instant to say “Connect Google Drive and Signal Studio can show the file's name and type instead of a bare link.” Earned, not begged.

The surface this lands on, today

Intake — one affordance, three paths

The current section is genuinely good: a single input that is both drop zone and link field. Do not add a third row. “Attach” becomes a two-item menu — Upload from computer / Add from Drive — and the drop zone and paste field stay exactly as they are.

The delight beat, named deliberately

An upload shows Dropping → Uploading → Attached. A reference has no pending state at all: the Picker closes and the row is simply there. Per the north star's rule that delight gets an explicit verdict — animate: the row settles in with the existing 200 ms EASE_OUT_TOKEN entry and no spinner ever appears. Instantaneity is the feature; do not fake a progress bar to make the two paths look alike.

Which actions Signal owns

Signal owns Remove from task and its own display label. Drive owns Rename, Move, Delete, Share and previewing its native documents. Signal must never offer a “Delete permanently” that reaches into someone's Drive — there is no version of that button that is safe to get wrong.

Disconnect, said plainly

Before the confirm, not after: “Your files stay in Google Drive. Signal Studio will stop showing their names, and these links will need reconnecting. Nothing is deleted.” Then name the count — “14 resources across 3 projects will show as unavailable.”

Phase 7 · threat model

The repo has no cryptography helper of any kind today, and calendar_connections stores its refresh token in plaintext relying on Turso's at-rest encryption. For a grant that reaches a user's documents, that is not sufficient — and fixing it is a prerequisite, not a follow-up.

Phase 9 · scope

The smallest genuinely valuable version

In the MVP

  • ✓Connect Google Drive in Settings → Connections. drive.file only, per user, encrypted refresh token, connect / disconnect / reconnect
  • ✓Add from Drive on a task, via the Google Picker. Writes one resources row: kind='link', storage='reference', provider from the mime type, external_id, countsAgainstStorage=0
  • ✓Lazy metadata refresh on open, with accessState moving to unavailable on 404 or 403, and a plain sentence for each state
  • ✓Migration 0028 — the three additive columns, the partial unique index, and provider_connections
  • ✓Native upload untouched as the default and the no-connection path
  • ✓Erasure and export wiring from day one, following notes-gdpr.ts's established order

Explicitly not in the MVP

  • ✕Uploading anything into Drive. No file creation, no folder tree, no project↔folder mapping, no resumable uploads
  • ✕Two-way sync, webhooks, changes.watch, any background reconciler
  • ✕Previews, thumbnails or any remote image fetch
  • ✕Shared Drives, OneDrive, SharePoint, Dropbox
  • ✕Project-level document libraries — the nullable task_id that enables them is deliberately deferred
  • ✕Version awareness, file search, AI summarisation or extraction, automatic task↔document linking
  • ✕Propagating Drive permissions to Project members
  • ✕Exposing any resource on a public, share, print or embed surface
  • ✕Retiring the attachments table
What this buys later, for free

Nullable task_id turns into project document libraries with no new table. provider plus provider_connections takes OneDrive, SharePoint and Dropbox without a schema change. storage='signal'|'reference' is the seam a Signal-managed or team-owned store would slot into. None of it needs building now, and all of it stays reachable.
